# HiDream-I1-Full GPU admission on the shared 8x L20 host (2026-09-18)

## Question

Can the native `HiDreamImagePipeline` actually be served on 2x L20 (46 GB), TP=2,
BF16, batch=1 — the candidate E2E environment for the Phase B resolution work?

## Verdict

**No.** TP=2 does not reach readiness; both ranks die with `torch.OutOfMemoryError`
while the pipeline is still being *constructed*, i.e. before any Phase B code path
runs. This is an existing capability limit of the box, not a regression from the
resolution change.

## Evidence

Session: `patch-eager-2xl20-tp2`, GPUs 1 and 3, `--tensor-parallel-size 2`,
`--enforce-eager`, local checkpoint `/experiment/models/hidream` (revision
`8ccbbfb270ccdae26d6bb0081df67dc81e4033bf`) and local auxiliary encoder
`/experiment/models/llama` (NousResearch mirror, revision `d10aef7999a2b5ba950ab3974312feeedbfe0b77`).

Server: `vllm_omni.entrypoints.cli.main serve ... --omni --tensor-parallel-size 2 --enforce-eager`

Observed sequence:

1. All four text encoders load on both ranks (CLIP-L 197 tensors, CLIP-G 517,
   T5-XXL 219, Llama-3.1-8B).
2. Per-GPU usage climbs to 37.7 GB on both ranks before the transformer is built.
3. `HiDreamImageTransformer2DModel.__init__` fails in
   `MOEFeedForwardSwiGLU` / `HiDreamImageFeedForwardSwiGLU` (`nn.Linear` for the
   first routed expert) with

   ```
   torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 34.00 MiB.
   GPU 0 has a total capacity of 44.40 GiB of which 2.00 MiB is free.
   Including non-PyTorch memory, this process has 33.81 GiB memory in use.
   ```

   and the same on GPU 1 (34.08 GiB in use).
4. Both `DiffusionWorker_TP0`/`TP1` processes exit; the orchestrator reports
   `RuntimeError: Orchestrator initialization failed:` over an `EOFError`, and the
   API server exits with code 2.

Peak per-GPU samples (`evidence/patch-eager-2xl20-tp2/gpu_samples.jsonl`):
GPU 1 = 37705 MiB, GPU 3 = 37484 MiB, immediately before the workers die.

## TP=4 was also tried, and also OOMs

Session `patch-eager-tp4-20260918`, GPUs 0-3, `--tensor-parallel-size 4`,
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. The workers again die inside
`HiDreamImageTransformer2DModel.__init__` -> `MOEFeedForwardSwiGLU` ->
`HiDreamImageFeedForwardSwiGLU.w3`:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 76.00 MiB.
GPU 2 has a total capacity of 44.40 GiB of which 50.62 MiB is free.
Including non-PyTorch memory, this process has 44.27 GiB memory in use.
Of the allocated memory 43.93 GiB is allocated by PyTorch
```

(GPU 0 reports 38.58 GiB in use with a foreign process holding the rest.)

## Why more TP ranks do not rescue it

- The 4 text encoders (CLIP-L, CLIP-G, T5-XXL, Llama-3.1-8B) are loaded **in full on
  every TP rank**. That is ~29 GB of weights per rank before the DiT is built.
- The DiT is only partly tensor-parallel. `HiDreamAttention` uses
  `QKVParallelLinear` / `RowParallelLinear`, but the MoE feed-forward that dominates
  the 34 GB is plain `torch.nn.Linear`:
  `HiDreamImageFeedForwardSwiGLU` builds `w1/w2/w3` with `nn.Linear`, and
  `MOEFeedForwardSwiGLU` instantiates one shared plus `num_routed_experts=4` routed
  copies of it per block. Those tensors are replicated on every rank, so raising TP
  does **not** shrink them.
- Consequently per-rank demand is roughly `text_encoders + 34 GiB` (plus the small
  sharded attention share), i.e. ~60 GiB and up, which no TP degree fits into
  44.4 GiB of usable L20 memory.
- `--text-encoder-tp-size` is implemented per model (MiniMax-H3 shards its encoder,
  SANA-Video rejects the flag); the HiDream pipeline has no such path.
- `--enable-cpu-offload` / `--enable-layerwise-offload` are not implemented for the
  HiDream pipeline, so they cannot shrink the resident set without changing the model
  or adding an offload feature, both of which are explicitly out of scope.

The single-card reference recipe (1x 80 GB) needs ~67 GB on one device, which the
48 GB-class L20 cannot provide at any TP degree.

## Consequence for this change

The Phase B contract is validated on CPU (unit + serving pre-dispatch tests) and
statically against the real checkpoint geometry. The GPU size matrix stays
`NOT RUN` on this host, and the existing H100 weekly E2E stays skipped: neither
"the default online mode supports custom sizes" nor "the weekly test passes" is
claimed.
